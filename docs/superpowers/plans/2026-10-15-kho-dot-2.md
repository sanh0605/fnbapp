## What was built, 2026-10-15 (differences from the tickets above)

- **S2:** one function, `save_purchased_item_atomic` (migration `0124`, not run), covers both add and edit, the way `save_product_atomic` does. A removed conversion that a purchase line points at is set INACTIVE inside the database instead of being deleted, so the "is it used" check cannot go stale.
- **The order edit trail stays.** `purchase_order_edits` (20 rows) has no reader except the two backup copiers, but it is the only record of who changed a purchase order. Opus decision: keep writing it as today, and move the write inside `save_purchase_order_atomic` in the structure batch.
- **S1:** a line quantity of 0 stays legal, because a draft stores an empty Số lượng box as 0 (`BR-UI-009`); the database check is `quantity >= 0`, and the action refuses 0 only on a completed order, as before. The money check covers all six columns, `subtotal_amount` and `voucher_amount` included. Disposals are a plain insert, not an rpc, so the race-safe guard is a `before insert` trigger on `asset_disposals` that locks the asset row. `lib/purchasing/purchase-order-write-plan.ts` needed no change.
- **S2 (Opus review):** the conversion update also requires the row to belong to the item being saved, so a foreign id sent by the form changes nothing.
- **G1:** dates use the shared formatter, so a day-only date reads "04/04/2026 00:00:00" (`BR-DATA-006`, owner 2026-09-29). The warning boxes are the shared `Alert`, which a screen reader announces as an alert instead of a status.
